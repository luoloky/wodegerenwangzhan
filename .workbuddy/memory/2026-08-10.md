# 2026-08-10 视频“加载太卡”治理

## 现象
用户再次反馈首屏视频“加载还是太卡”。上一轮已做：fixed 背景、去 mix-blend-mode、去 fog blur、暂停滚动解码。

## 真正根因
首屏视频用 `data-src` + `requestIdleCallback(loadVideo, { timeout: 2000 })` 懒加载。
首屏 GSAP 进场动画占满主线程约 2s，`requestIdleCallback` 迟迟不触发 → 视频 2~4s 后才开始加载，
再叠加 `preload="none"` 与 0.9s 淡入 → 体感“加载太慢”。这与“为减卡顿而懒加载”自相矛盾。

## 排除项（确认不是这些问题）
- 视频文件仅 1.35MB（public/videos/hero-bg.mp4），不算大。
- public/_headers 已配 `/videos/*  Cache-Control: public, max-age=2592000`，线上缓存 OK。
- 所以瓶颈是“加载逻辑”，不是“文件大/没缓存”。

## 修复（src/components/Hero.jsx）
- `<video>` 改回直接用 `src="/videos/hero-bg.mp4"` + `autoPlay` + `preload="auto"`（立即加载），
  删除 `data-src` 与 `preload="none"`。
- 删除第二个 useEffect（requestIdleCallback 懒加载逻辑）。
- 保留：canplay 后 `.is-ready` 淡入、手势 fallback 播放、滚动时暂停解码（前几轮性能成果不动）。
- 已 `npm run build` 通过（dist/index-C1QNMa9b.js）。

## 项目区两个视频“点开加载慢”修复（同日追加）
- 用户澄清：卡的是**项目经历里的两个视频**（public/videos/slxws-video.mp4 19MB、ue-emm-walkthrough.mp4 10MB），要“点击立即播”。
- 代码侧（src/components/Projects.jsx 的 LazyVideo）此前已改：进视口（rootMargin 200px）即挂 src + `preload="auto"` + 主动 `load()`，点开前已预缓冲。
- 硬伤：两个文件都**无 faststart**（moov 在文件末尾），浏览器须下完整个文件才开播，preload 也救不了。
- **没用 ffmpeg**：网络通了但 GitHub 被限流到 ~10KB/s（106MB 二进制 280s 只下 3MB），不可行。
- 改用**纯 JS qt-faststart 重封装**（自写 tmp_faststart.cjs，已删除）：解析原子、把 moov 移到文件头、对 stco/co64 分块偏移 +moovSize。
  两文件字节长度完全不变（无损），moov 已移到 mdat 之前；再用 tmp_verify.cjs 校验 17258+46 个分块偏移全部落在 mdat 区间内（0 越界）。
- 原始文件移出 public/ 到 `.video-originals/`（避免被部署/被 git 提交，且可随时找回重编码）。
- 已 `npm run build` 通过，dist/videos 已是 faststart 版。
- 结论：faststart + preload="auto" 后，滚到项目即后台预缓冲，点击播放应近即时开播。若还想更快，可把文件压到更小码率（需 ffmpeg）。

## ffmpeg 本地部署成功（同日追加）
- 用户从 GitHub(BtbN/FFmpeg-Builds) 下载 `ffmpeg-master-latest-win64-gpl-shared`，解压到 `D:\ffmpeg-master-latest-win64-gpl-shared\`（D 盘根目录，无需装 PATH，绝对路径调用即可）。
- 验证可用：`D:\ffmpeg-master-latest-win64-gpl-shared\bin\ffmpeg.exe -version` 正常，编译带 `--enable-libx264`。
- **压缩结果**：
  - ue-emm-walkthrough：1920x1080/5511kb/s/10MB → `scale=1280:-2, crf26` → **2.7MB**（码率 1473kb/s），瘦身 73%。
  - slxws-video：960x544/393kb/s/19MB（已 faststart）。尝试 `crf30` 反而变 25.6MB（608kb/s，源本就低码率，重编码更肥）→ **还原回 19MB 的 faststart 版**（更小且已能点开即播）。
- 注意：ffmpeg `-vf "scale=min(960,iw):-2"` 中的括号会被 shell 吞掉报 `No such filter: 'iw):-2'`，改用 `scale=960:-2` 直接指定宽度。
- 最终 public/videos：hero-bg.mp4 1.35MB、slxws-video.mp4 19MB(faststart)、ue-emm-walkthrough.mp4 2.7MB(faststart)；两项目视频均 FASTSTART ✓。
- `npm run build` 通过，dist/videos 已更新。dev server 仍在线(HTTP 200)。
- **教训**：低码率源视频不宜盲目重编码（易变大）；faststart 才是“点开即播”的关键。大分辨率高码率视频（如 1080p/5.5Mbps 短视频）压到 720p 收益最大。
